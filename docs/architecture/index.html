hotel-curator architecture

An offline pipeline makes labels, models and hotel results; an online stack serves them. The two halves meet only at a handful of committed files. The Mermaid versions of these views, with tables, are in README.md, offline.md and online.md.

1. Offline and online

The offline half runs by hand with the curator CLI. Its outputs that the online half needs are committed; the API image copies them at build time, and the API reads them at start-up (and promotion.json again for GET /v1/meta). Nothing online trains, reads the raw dataset or calls an LLM.

2. Offline pipeline

Every stage except the LLM annotator panel is a curator command. Inputs are pinned by SHA-256. The data, label and scoring stages write manifests under data/manifests/ with the SHA-256 of each output (the data manifest also hashes each input chunk); the model stages write reports under artifacts/evals/, and the package files are tied to the promotion decision by their hashes. The promotion rule and the tier scheme were committed before any model ran.

3. Online on a laptop: docker compose

docker compose up runs the same three images on one machine. The web container serves the app; the API is also published on 127.0.0.1:8000 (docs and direct API) for local use. Postgres has no network: it listens only on a Unix socket in a volume that only the db and API containers mount. Over that socket the API's role, which is not a superuser, connects; the superuser only by peer authentication, from inside the db container.

4. Production on Fly.io

Three Fly apps in lhr, one machine each (ADR 011). Only the web app has public addresses. It reaches the API through Flycast, Fly's private load-balanced address, and the API reaches Postgres by its .internal name over TLS. Before the Cloudflare cutover, visitors reach Fly's edge directly (Fly mode); after it, Cloudflare terminates their TLS and passes requests to the origin over TLS with its client certificate, which Fly passes through untouched (Cloudflare mode). Deploys from GitHub come only from CI on main, after the owner approves them; the database app, the first deploy and manual redeploys run by hand with scripts/deploy.py, and an API rollback redeploys an earlier image with flyctl deploy --image.

5. Request flow: a hotel page

Hotel results are computed offline; the hotel itself is one primary-key lookup of the stored detail and a schema-validated JSON response (the app shell also fetches /v1/meta and /v1/cities). Live inference happens only for POST /v1/analyze, which stores nothing and does not echo text.
